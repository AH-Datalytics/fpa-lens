## Data Refresh Automation
- Daily GitHub Action `.github/workflows/refresh-data.yml` (`cron: 0 13 * * 1-5`, weekday mornings ~8am Central; also `workflow_dispatch`) pulls the newest source files from the SharePoint `LensRepository`, regenerates the dashboard JSON in `public/data/` (+ `src/data/turfCycles.json`), commits only what changed, and lets Vercel auto-deploy. Orchestrator: `scripts/refresh-data.mjs`; SharePoint auth/fetch in `scripts/sharepoint/`. Categories: finance, idiq, safety, staffing, sitrep, turf. Full design in `docs/data-automation-plan.md`.
- **Digest email** (`scripts/notify-digest.mjs`, unit-tested via `notify-digest.test.mjs`): one email to Oscar (Resend, from `alerts@fpalens.org`), reporting data changes published that run (diffed from the working tree vs HEAD), per-source pull status (REFRESHED/SKIPPED/FAILED), and any failures. Runs `if: always()` before the commit step and never fails the job. It replaced the earlier failure-only and SITREP-roll-only emails (July 2026). **Send policy is `shouldSend()`, not every run** (changed Aug 2026 with the daily cron): it emails when data published, when a source FAILED or the run errored, or when `FORCE_DIGEST=1` — which the workflow sets for `workflow_dispatch`, so a manual run always confirms. A clean scheduled run that found nothing new is silent, so five weekday runs don't bury the one that matters. If you ever want confirmation of a quiet day, dispatch it by hand.
- SharePoint creds live in Vercel + GitHub secrets (`SHAREPOINT_*`). For local pipeline runs, `graph.mjs` reads them from `.env.vercel-prod` (gitignored) -- hydrate it with `vercel env pull .env.vercel-prod --environment=production`.

## Content Management (CMS): Payload at `/admin`
- Payload 3 lives inside this app and lets FPA staff edit **curated** content (home hero copy, staff/leadership cards + photos, footer/contact) with no code. It does NOT touch automated data (finance/safety/turf/readiness/permits) -- those stay on the SharePoint pipeline. Full ops notes: `docs/cms-notes.md` (with `cms-checklist.md` / `cms-completed.md`).
- **Read path:** public pages read via `src/lib/cms.ts` helpers (wrapped in `unstable_cache`, tag `"cms"`), each falling back to `src/data/siteData.ts` on any error, so the site always renders. Pages are ISR (`revalidate = 60`); a Payload afterChange hook (`src/lib/revalidateCms.ts`) calls `updateTag("cms")` for near-instant updates. Live Preview iframe is enabled (so `next.config.ts` uses `X-Frame-Options: SAMEORIGIN`, not DENY); turning it on in the admin updates page copy *as you type*, before Save, via `@payloadcms/live-preview-react`'s `useLivePreview` inside the `usePageCopy` hook. `RefreshRouteOnSave` stays the save-time fallback for Staff and Footer/Site Settings (those update on save, not keystroke-live).
- **Page copy:** every page's editable prose is a per-page global under the admin "Page Content" group (`src/globals/pages/*.ts`, registered via `pages/index.ts` -> `pageGlobals`). Each field's `defaultValue` is the current wording, so unsaved globals return the text and there's no visual change / no seed. All pages now read copy via the `usePageCopy(slug, DEFAULTS)` client hook (`src/lib/usePageCopy.ts`, fetches `/api/globals/<slug>`); About/Protection (and the home hero) were converted from server `getPageContent` to Client Components so they get real-time Live Preview too. Data/numbers/labels stay code-driven. Full pattern in `docs/cms-notes.md` §8a.
- **What's editable (prose only):** editors can change page/section headings, body/intro/callout paragraphs, and staff bios + photos. Everything else is hardcoded in the page and NOT editable: data/numbers, chart/card/metric titles, status legends and values, thresholds, nav/button/tab labels, tooltips, abbreviation expansions (e.g. LNO), process-step labels, prose that embeds live data, and AHD-authored data-source / sourcing / methodology notes. A 2026-07-06 audit trimmed 65 such fields back to hardcoded literals. Editable-field counts per page: about 49, finance 5, safety 10, engineering 8, environment 15, infrastructure 13, protection 8, staffing 6, turf 11, idiq 13, permits 3 (pageTitle, intro, lifecycleHeading — added July 2026); `HomeContent` is just the hero headline.
- **Admin dashboard:** `/admin` uses a custom dashboard view (`src/components/admin/Dashboard.tsx`, wired via `admin.components.views.dashboard`): a welcome header, a how-to-use guide, and grouped, described cards (Website pages / People, home & settings / Portal administration). The Portal administration (Users) group is admin-only. **Those cards are a hardcoded `PAGE_CARDS` array, not derived from the registered globals**, so shipping a new page global leaves it reachable from the left nav but invisible on the `/admin` landing page most editors start from. Add a card in the same commit. This was missed for Permits (July 2026) and only caught when Tropical Weather shipped in August; both were backfilled then. Checking prod for a new page global takes two steps: `/api/globals/<slug>` returning 200 proves the Neon table exists, and the card proves an editor can actually find it.
- **Structure:** `src/payload.config.ts`; collections `Users` (auth, `admin`/`editor` roles), `Media`, `StaffMembers`; globals `SiteSettings`, `HomeContent`, and the per-page `pages/*` globals. Route groups: existing site under `src/app/(frontend)/`, admin under `src/app/(payload)/`. `package.json` is `"type": "module"` (required for the Payload CLI); after changing admin components/config run `CMS_MEDIA_BLOB_TOKEN="$BLOB_READ_WRITE_TOKEN" npx payload generate:importmap` and `generate:types`. **IMPORTANT importMap trap (has bitten twice):** `generate:importmap` AND `next build` both regenerate `importMap.js`, and if the blob plugin is off during that run they strip `VercelBlobClientUploadHandler`; prod has the blob plugin ON, so a stripped map means the **entire prod admin renders blank** (login + reset included, **0 client-side errors** — the real `getFromImportMap ... not found` error is server-side, visible only in `vercel logs --scope ahdatalytics`). So: (1) always regenerate with `CMS_MEDIA_BLOB_TOKEN` set to a **valid-format** token (the lakefront `BLOB_READ_WRITE_TOKEN` works — a fake/dummy token fails the adapter's format check), and **`export` the var** rather than inline-prefixing it: the inline `CMS_MEDIA_BLOB_TOKEN=... npx payload generate:importmap` form silently did NOT propagate through the CLI's exec (blob handler stayed stripped, no error). Use `export CMS_MEDIA_BLOB_TOKEN=$(grep '^BLOB_READ_WRITE_TOKEN=' .env.vercel-prod | cut -d= -f2- | tr -d '"'); npx payload generate:importmap`; (2) do NOT run a plain `next build` before committing (it re-strips the map) unless you set the token; (3) before committing, grep `importMap.js` **separately** for `VercelBlobClientUploadHandler`, the Lexical `RscEntryLexicalField`, and — when the editor's toolbar feature changed — `FixedToolbarFeatureClient`, confirming each appears twice (import + map entry); a single `grep -c` with an alternation is ambiguous; (4) after any admin/config deploy, browser-check `/admin` on prod (a real page render, not just an HTTP 200). If the git webhook doesn't auto-deploy within a few minutes, `vercel --prod --scope ahdatalytics --yes` builds the committed state (the remote build has the blob token, so its importMap regenerates correctly).
- **DB:** local dev = SQLite (`.env.local`: `PAYLOAD_SECRET` + `DATABASE_URI=file:./cms-dev.db`), isolated from prod. Prod = Neon Postgres (`POSTGRES_URL`, auto-selected when set). Config picks the adapter by `POSTGRES_URL` presence.
- **Media/photos:** dedicated **public** Vercel Blob store via `CMS_MEDIA_BLOB_TOKEN` -- kept separate from the lakefront `BLOB_READ_WRITE_TOKEN` store (do not merge them; `forecastStore.ts`/`riskAlertStore.ts` use the lakefront one). Plugin enables when `CMS_MEDIA_BLOB_TOKEN` is set; local dev without it uses disk / curated `/headshots`.
  - **Headshots render through the Next image optimizer, so their host MUST be in `next.config.ts` `images.remotePatterns`.** Payload serves uploaded media (proxied) from the app's **own domain** (`https://fpalens.org/api/media/file/*`), NOT the blob host -- so `remotePatterns` allowlists `fpalens.org` + `www.fpalens.org` alongside `*.public.blob.vercel-storage.com`. If the site domain changes, or a new image host is introduced and isn't allowlisted, the optimizer returns **400 and every CMS headshot renders blank** (curated relative `/headshots/*` are unaffected, which makes it look intermittent). This bit us July 2026 -- all `/about` leadership photos were blank because only the blob host was allowlisted. After any domain/media change, verify: `curl -s -o /dev/null -w '%{http_code}' 'https://www.fpalens.org/_next/image?url=<url-encoded-media-url>&w=256&q=75'` must return `200`, not `400`.
- **Seed:** `scripts/seed-cms.ts` (idempotent, `payload run`) populates content + the editors from `siteData.ts` (Jeff Williams is seeded as `admin`), and idempotently re-enforces each user's role on re-run. Add `SEED_DEV_ADMIN=1` for a local `dev@fpalens.local`/`devpassword123` admin (never in prod). Seed prod against Neon's **direct/unpooled** string (the pooled/sensitive vars can't be pulled via CLI). `scripts/set-password.ts` grants initial access before the Resend "Forgot password" flow.
- **Editing CMS-backed content in prod (e.g. `staff-members` / leadership tiles):** the live About/leadership tiles come from the Payload `staff-members` collection in **prod Neon**, NOT `siteData.ts`. `siteData.ts` is only the fallback + seed source + curated-image-by-name map -- keep it in sync, but edits there **do not change the live site**. Because the seed upserts by name and never deletes, removals/renames need a targeted one-off script (see `scripts/update-staff-personnel.ts`, following the `set-role.ts`/`push-schema.ts` pattern). **Trap (bit us July 2026):** `vercel env pull` leaves every `POSTGRES_*` value BLANK in `.env.vercel-prod` (they're Sensitive), so a `payload run` script with an empty `POSTGRES_URL` **silently falls back to local SQLite (`cms-dev.db`) and prod is untouched** while the run still logs "success." Always pass the **unpooled** Neon string from the Vercel -> Storage -> `fpa-lens-cms` (Neon) dashboard (`?sslmode=require`, no `channel_binding`) and confirm the run prints a `*.neon.tech` target host before trusting it. The REST API (`/api/staff-members`) reflects DB writes immediately; the `/about` page ISR-refreshes within ~60s.
- **Roles & editors:** two roles: `admin` (AH Datalytics accounts; manage the editor roster + all content) and `editor` (content only). The Users collection is `admin.hidden` from editors, so they don't see the roster in the nav and manage their own login via the Account page. Editors are otherwise managed in-panel; invites/resets email via the existing `RESEND_API_KEY`. **Jeff Williams (`jwilliams@slfpae.gov`) is an admin.** `scripts/set-role.ts` sets a user's role.

### Safety (/safety)
- Reporting period is calendar year (Jan 1 - Dec 31) per Director and Safety Officer direction, Apr 2026.
- Per Safety Officer (Jamal) Apr 2026 reclassification, each event's classification is encoded in the fill color of the Recordable cell:

  - Light blue (`FF00B0F0`) = No-Fault → counted in totals only; excluded from performance metrics and the YoY accident chart

Every year sums exactly to its yearly override. No-fault monthly counts stay event-log-derived (not part of his breakdown); injuries are tracked only at the year level.

Because 2026 accidents/incidents/injuries are now override-driven, **when Jamal sends a new monthly file, update BOTH override tables** — the weekly event-log refresh no longer moves those three counts for the live year (it still updates no-fault, lost time, and property damage). ### Turf Maintenance (/infrastructure/turf-maintenance)
- Built out May 2026. Covers all three levee districts: Orleans (OLD, 6 zones, 1,620 ac), East Jefferson (EJLD, 4 zones, 660 ac), and Lake Borgne Basin (LBBLD, 4 zones, 1,353 ac). 3,633 acres / 14 zones total.
- Page leads with the maintenance plan (Jeff's verbiage: "SLFPA-East maintains 3,633 acres of levee turf across 14 zones in three levee districts. Mowing targets vary by zone... This dashboard shows monthly progress against those targets using a simple Green / Amber / Red status"), then a district filter that scopes both the map and the per-zone cards below it. Default filter is OLD. The old "Cycle 1 complete" status strip + per-district zoneCount cards were removed in May 2026 once OLD started logging Cycle 2 — per-zone Green/Amber/Red is now the single source of truth.
- Per-zone cards (redesigned May 2026, second pass per Director feedback): focus on a single question — *how much of the monthly cutting goal has been completed?* Header shows acres, cycles/mo, and the monthly target. Body shows a Reach list (renamed from "Coverage") with per-reach acreage, then a single progress bar headlined "X of Y acres completed this month" with a Cycle 1 tick mark and a Green/Amber/Red badge. Projection math, acres-per-day pace, Cycle 1 dates, and working-day counts are all hidden. Zones with no reported actuals show an "Awaiting weekly update" gray state.
- Data model (`src/data/grassCutting.ts`): each zone carries `reaches: Reach[]` (name, acres, `cycle1Pct`, `cycle2Pct`) and `hasReportedData: boolean`. `cycle1Pct`/`cycle2Pct` are cumulative percent-complete from the maintenance team's weekly workbook (max value across the month's weeks per cycle). `cycle2Pct` is `null` for 1×/mo zones (LBBLD). A `reportingMonth` field on `grassCuttingData` (`{ label, year, month, isComplete }`) drives the period the cards report against.
- KPI helpers (`src/lib/turfMaintenance.ts`):
  - `monthlyTargetAcres = zone.acres × monthlyFrequency`
  - `monthAcresDone = Σ reach.acres × (cycle1Pct + (cycle2Pct ?? 0))`
  - `computeMonthlyKpi`: when `reportingMonth.isComplete`, level is set on raw `done/target`. When the month is in flight, level is pace-adjusted by `done / (elapsedFraction × target)`. Thresholds: Green ≥ 90%, Amber 80–89%, Red < 80% (Director confirmed May 7, 2026).
  - `cycle1TickPosition = 1 / monthlyFrequency`, returns `null` for 1×/mo (no intermediate tick — the bar *is* the cycle). Director confirmed May 7, 2026.
- System-wide rollup (the badge on the infrastructure-page turf card and on the turf-maintenance page System overview) uses the same 90/80 thresholds applied to the on-pace zone ratio (`greenZones / totalZones`). Not worst-of -- a single off-pace zone in a 14-zone system shouldn't drag the rollup to Red. Both `src/lib/readinessRollups.ts` and `src/app/infrastructure/page.tsx` keep this in sync.
- Source data:

  - Weekly C1/C2 percentages now flow from the **FPA Turf Maintenance Input Template** (Jeff's Excel workbook with Orleans / East Jefferson / Lake Borgne Basin tabs), columns G/J/M/P/S = weekly C1 % and H/K/N/Q/T = weekly C2 % across up to five week-ending columns. The legacy "New Cutting Plan 2026" / "Mileage log" tabs are no longer the source of truth for percentages, only for the Cycle 1 historic dates carried in `oldCycle1` / `ejldCycle1` / `lbbldCycle1` summaries.

### Tropical Weather (/environment/tropical-weather)
- Live National Hurricane Center dashboard: forecast cone/track, model spread, coastal watches and warnings, New Orleans wind probabilities, and the seven-day genesis outlook. Reached from the Environment nav dropdown and a button at the top of `/environment`. Ported August 2026 from Jeff Asher's standalone [AH-Datalytics/gulf-watch](https://github.com/AH-Datalytics/gulf-watch) build, which FPA asked to have folded into Lens.
- **Two modes, driven by the data, not by us.** `manifest.json`'s `mode` is `quiet` (no active systems -> outlook prose + a "no formation expected" card on the map) or `active` (storm header, warnings, wind probabilities, model tracks). Most of the year it is quiet, so the quiet view is the one to check first after any change.
- **Data path is blob, not SharePoint and not the repo.** `ingest/` (Python, `gulfwatch` package kept from upstream) runs on `.github/workflows/tropical-ingest.yml` (cron `7,22,37,52 * * * *`), normalizes NHC products, and PUTs them to a dedicated public Vercel Blob store; the browser reads `manifest.json` straight from that store. No deploy, no commit, nothing in `public/data/`. Per-product failures land in the manifest's `errors` list and surface in the rail's "Some products are temporarily unavailable" disclosure. See `ingest/README.md`.
- **Three blob stores now, never interchangeable.** This one is `fpa-tropical` (`store_yAYQazt9SKO3Nvio`, public, iad1), base URL `https://yayqazt9sko3nvio.public.blob.vercel-storage.com`. It is already provisioned, connected to the `fpa-lens` Vercel project with env-var prefix `TROPICAL`, and populated.
  - `TROPICAL_READ_WRITE_TOKEN` — write token. Auto-created on the Vercel project by the store connection; the **same name** is a GitHub Actions secret, which is the one the ingest actually uses.
  - `TROPICAL_BLOB_BASE_URL` — GitHub Actions secret, the ingest's read base.
  - `NEXT_PUBLIC_TROPICAL_BLOB_BASE_URL` — Vercel (all three environments), same value, read by the browser.
  - The other two stores are `BLOB_READ_WRITE_TOKEN` (lakefront forecast/alert state, `store_e0jJ...`) and `CMS_MEDIA_BLOB_TOKEN` (Payload media). **Connecting a new store via the Vercel dashboard/API without setting an env-var prefix writes a bare `BLOB_READ_WRITE_TOKEN` and silently repoints the lakefront store** — always pass a prefix (the API field is `envVarPrefix` on `POST /v1/storage/stores/{id}/connections`).
  - With the base URL unset the page degrades honestly: basemap plus "Live conditions unavailable — do not interpret this as an all-clear". It does not crash or imply calm.
- **Ported code lives in three places**: `src/lib/tropical/` (data layer + cartography, upstream logic largely intact, unit-tested), `src/components/tropical/` (every panel rebuilt in Tailwind against the FPA palette — the upstream 2,500-line hand-written CSS theme is gone), and the route under `src/app/(frontend)/environment/tropical-weather/`. Only genuinely map-internal chrome (MapLibre `Marker` elements built with `document.createElement`, which Tailwind can't reach) stays as CSS, in that route's `tropical-map.css` under a `tmap-` prefix.
- **MapLibre traps, both already paid for:**
  - The map container must be sized with `h-full w-full`, never `absolute inset-0`. MapLibre stamps `.maplibregl-map { position: relative }` on it from `maplibre-gl.css`, which loads after the Tailwind utilities and wins on equal specificity, so an `absolute` utility silently collapses the container to zero height and the map renders at canvas's 300px default.
  - `public/maplibre-gl-worker.mjs` + `maplibre-gl-shared.mjs` are verbatim copies of the installed dist files, needed because MapLibre's own worker-URL resolution breaks under Turbopack (the map then hangs with no error). **Re-copy both whenever `maplibre-gl` is bumped** — `scripts/check-maplibre-worker-sync.mjs` runs on `predev`/`prebuild` and fails loudly if they drift.
- **Demos**: `?demo=ida` replays real Hurricane Ida advisories 5-15 (fixtures in `public/tropical/demo/`, ~15 MB) and `?demo=quiet` a simulated calm manifest. The quiet rail links to the Ida demo so visitors can see the storm view out of season. Demo mode shows an amber "HISTORICAL SAMPLE" banner above the map and never fires the staleness warning.

### Completed Implementation
- Core risk engine with 4-tier system (GREEN/YELLOW/ORANGE/RED)
- Wind duration gating: YELLOW and ORANGE require 70% sustained onshore winds over 3-hour window (~2.1 hrs effective). RED triggers immediately. Falls back to instantaneous-only if wind history unavailable.
- **Alert email policy** (`src/lib/riskAlertDecision.ts`, used by the 5-min cron `api/cron/collect-forecasts`): decisions key off the last *notified* level (persisted only when a send succeeds), NOT the last observed level — so an "all clear" fires solely to clear an alert we actually sent (fixes repeated all-clear spam from transient spikes). Only ORANGE/RED are alert-worthy; YELLOW is routine and never emails (alerts fire crossing into/out of the ORANGE+ band). Trend-gated in both directions including RED (skip improving escalations / worsening de-escalations), so an escalation into RED that is already improving is treated as a receding spike and suppressed. Pure logic is unit-tested (`riskAlertDecision.test.ts`).
- Environmental page shows persistence info in wind card and threshold table footnote
- All methodology documented in JSDoc comments in lakefrontRisk.ts
- **Split wind/water charts**: Separate stacked charts sharing same time axis
- **Configurable observed window**: Time range selector (6h/12h/24h/48h/72h) re-fetches API with `?range=N`. Default 24h observed + 2-day forecast. Auto-scaling thinning per range.
- **Chart controls**: PNG download, CSV download, date-annotated X-axis, threshold annotations
- **Forecast snapshot storage** (`src/lib/forecastStore.ts`): Saves first-seen forecast per target hour to `data/forecast-history.json`. 7-day retention. Toggle to overlay original forecast over observed data. Both "first seen" (~48h lead) and `forecast24h` (22-26h lead) strategies stored.
